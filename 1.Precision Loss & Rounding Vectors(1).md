# Precision Loss & Rounding Vectors(1)

## 1. Business Logic Rules

This is a minimal vault business contract. Users deposit assets into the Vault and receive shares in return; users who hold shares can redeem them for assets. Based on these business rules, we discuss precision arbitrage and the impact of rounding direction.

## 2. State

| Variable | Meaning |
| --- | --- |
| `totalAssets` | Total assets managed by the Vault |
| `totalShares` | Total shares issued by the Vault |
| `sharesOf[user]` | Shares held by a user |
| `assets` | Assets deposited or redeemed in this transaction |
| `shares` | Shares minted or burned in this transaction |

## 3. Deposit Business Rules

Users deposit assets, and the Vault mints shares at the current exchange rate:

$$
shares = \frac{assets \times totalShares}{totalAssets}
$$

**Operation sequence**

1. Receive the user's assets
2. Compute `shares` from the pre-operation asset and share totals
3. Apply the specified rounding direction to the result
4. Update `totalAssets`
5. Update `totalShares`
6. Increase the user's share balance

## 4. Redeem Business Rules

Users burn shares, and the Vault pays out the corresponding assets:

$$
assets = \frac{shares \times totalAssets}{totalShares}
$$

**Operation sequence**

1. Check the user's share balance
2. Compute `assets` from the pre-redeem asset and share totals
3. Apply the specified rounding direction to the result
4. Burn the user's shares
5. Decrease `totalShares`
6. Decrease `totalAssets`
7. Pay out the assets

## 5. Hypothetical Attack Vectors

- Does rounding up grant new depositors extra equity?
- Does rounding down cause users to lose assets?
- Can insufficient share precision mint zero shares?
- Are the results of one operation and multiple split operations consistent?
- Can a deposit–redeem combination produce realizable arbitrage?

## 6. Verifying the Hypotheses

Next, we verify each of the hypothetical questions above, one by one.

### 6.1 Hypothesis 1: Rounding Up on Deposit

Does rounding up when minting shares on deposit grant new depositors extra equity?

**Business rule.** The Vault already holds liquidity from other users. When a new user deposits, the protocol mints shares by rounding up.

**Initial state**

| Parameter | Value |
| --- | --- |
| `totalAssets` | 101 |
| `totalShares` | 100 |
| User's shares | 50 |
| Attacker's deposit | 1 |

**Calculation**

Attacker deposits 1:

$$
shares = \left\lceil \frac{1 \times 100}{101} \right\rceil = 1
$$

After the deposit: `totalAssets = 102`, `totalShares = 101`. Attacker receives 1 share.

User's equity change:

- Before: $50 \times \frac{101}{100} = 50.5$
- After: $50 \times \frac{102}{101} = 50.4950495$
- User's loss: $50.5 - 50.4950495 = 0.0049505$

**Conclusion.** From the calculation, Attacker receives 1 share because rounding up turns a sub-1 result into 1. User loses 0.0049505 instead. If Attacker repeatedly deposits in small amounts, he can extract extra value. In a real audit, we still need to check whether fees and gas cover the trading cost — only then does this become a realistic attack incentive.

When auditing, do not stop at a single transaction. Sometimes you also need to compute the cumulative effect and check whether extra profit remains after many operations. Raising share precision alone cannot eliminate this vector at the mechanism level — it only shrinks each rounding error until the leftover is often uneconomical to exploit. Closing it properly still requires the correct rounding direction.

### 6.2 Hypothesis 2: Rounding on Redeem

Next, we look at the redeem case.

**Business rule.** The user already holds Vault shares, then makes a new deposit, and finally redeems all shares. Treat deposit and redeem as one full economic cycle — do not analyze redeem in isolation.

**Initial state**

| Parameter | Value |
| --- | --- |
| `totalAssets` | 102 |
| `totalShares` | 101 |
| User's existing shares | 50 |
| User's new deposit | 1 |

Deposit uses rounding up.

**Calculation**

Step 1 — user deposits 1:

$$
shares = \left\lceil \frac{1 \times 101}{102} \right\rceil = 1
$$

State becomes: `totalAssets = 103`, `totalShares = 102`. The user now holds 51 shares.

Step 2 — user redeems 51 shares:

In real numbers, the exact claim is:

$$
assets = \frac{51 \times 103}{102} = 51.5
$$

In this toy model, `totalAssets` / `totalShares` / payouts are already counted in atomic integer units. On-chain redeem with round-down is therefore integer division:

$$
assets = \left\lfloor \frac{51 \times 103}{102} \right\rfloor = 51
$$

Do not reinterpret `51.5` as a human-unit USDC amount with 6 decimals — that would require the vault balances themselves to be scaled (e.g. `102 × 10^6`), which this example does not do.

Step 3 — compare user equity:

- Value of the user's original 50 shares in the initial state: $50 \times \frac{102}{101} = 50.4950495$
- Plus the new deposit of 1: $50.4950495 + 1 = 51.4950495$
- Theoretical redeem proceeds: $51.5$
- Net profit: $51.5 - 51.4950495 = 0.0049505$

**My attack-vector reasoning**

1. After combining round-up on deposit and round-down on redeem, does the user profit?
2. Who bears the leftover rounding value?
3. If the user does not redeem and instead keeps holding shares, is the result the same?

**Conclusion.** Round-up on deposit plus round-down on redeem does not by itself imply a profitable arb. In this example the full cycle mints 1 share on deposit, then pays `⌊51 × 103 / 102⌋ = 51` on redeem. Against the cost basis ≈ 51.495, the user loses ≈ 0.495.
